# maolab 项目重启设计

日期：2026-06-30

## 0. 一句话结论

maolab 应该从“AI 课程生成工具箱”收拢回“把教材知识点变成一节真正能上的课”的产品。

重设计的核心不是继续增加角色、模板、导出、媒体、实时互动，而是建立一条稳定主线：

> 教材与知识点 → 教学骨架 → 可检查的课堂脚本 → 16:9 教学舞台 → 真实学习反馈。

所有不服务这条主线的功能，先降级为实验区或隔离区。

## 1. 背景

项目当前已经积累了大量有效能力：

- 教材与知识点对齐。
- 7 步课程创作流程。
- 教学骨架库。
- 片段化质量闸门。
- 老师、学生、TTS、立绘和课堂节拍。
- 互动课堂、授课模式、放映模式、自学模式、PPTX 导出。
- 真实检查流程和多轮修复记录。

问题也来自同一件事：能力增长太快，但产品秩序没有同步收敛。

当前偏离主要表现为：

- 目标从“能直接上一节课”漂移到“尽可能多的生成和播放能力”。
- 课堂形态太多：互动课堂、授课、放映、自学、live、showscript、media remix、PPTX，边界不清。
- 生成管线太多层规则互相补丁：rundown、script、atoms、beats、skeleton、fragment repair、present audit。
- 视觉系统持续被局部修补，缺少稳定版式语言。
- IP、对白、角色、媒体容易抢内容主体。
- 真实检查发现的问题被逐项修，但没有沉淀成更高层的产品取舍。

## 2. 重新定义产品

### 2.1 产品身份

maolab 是“猫叔的教学研究室”。

它不是：

- PPT 生成器。
- AI 视频包装器。
- 多智能体聊天课堂。
- 教材资料整理器。
- 课件模板市场。

它是：

- 面向老师和学生的 AI 备课与上课系统。
- 把国家教材知识点变成可讲、可看、可问、可复用的课堂片段。
- 用教学骨架和真实检查保证课程不跑偏。

### 2.2 目标用户

第一优先级：

- 需要快速备一节结构清楚课程的老师。
- 需要一个人被带着预习、补弱点或复习的学生。

第二优先级：

- 教研人员，用来检查知识点、教学路径和课程质量。
- 内容生产者，用来批量生成可审核课程片段。

暂不作为第一优先级：

- 只想导出精美 PPT 的用户。
- 只想生成短视频内容的用户。
- 需要实时多人直播课堂的用户。

## 3. 核心问题

当前项目真正要解决的问题不是“生成内容不够多”，而是：

1. 生成出来的课程能不能真的教会一个知识点。
2. 老师讲解、画面主体、学生反应能不能互相接上，形成“看见什么就讲什么，讲到哪里就看哪里”的关系。
3. 用户能不能判断这节课哪里好、哪里坏、怎么改。
4. 系统能不能稳定复用已经验证过的教学结构，而不是每次重新赌 LLM。

## 4. 设计原则

### 4.1 内容优先

任何声音、角色、图像、动画、对白都只能服务内容。

判断标准：

- 这一页学生要看什么？
- 老师正在指哪里？
- 学生为什么需要这一页？
- 去掉角色或装饰后，教学是否仍成立？

### 4.2 视讲同步

maolab 的课程体验必须服务视觉型学习者：学生先看到一个清楚对象，再听老师围绕这个对象讲解、追问和纠错。

每个教学画面都必须回答三件事：

- **看什么**：这一页的视觉焦点是什么。
- **听什么**：老师讲解正在解释视觉焦点的哪一部分。
- **怎么连上**：高亮、指向、局部放大、逐步显现或版式分区如何把讲解和画面连接起来。

禁止出现：

- 老师讲的内容不在画面上。
- 画面有重要内容，但讲解没有点到。
- 对白或角色遮住正在讲的对象。
- 先堆满材料，再靠老师口头解释关系。
- 每页都用同一种文字叠加方式，导致画面像被标注而不是被设计。

判断标准不是“画面漂不漂亮”，而是“学生能不能顺着老师的讲解看懂画面变化”。

### 4.3 板书文字

文字在教学中不是低级替代品，而是课堂板书层。

学生可能漏听讲解，也可能需要在讲解之后回看结构。板书文字的作用是把一节课里不能丢的提纲、关键词、步骤、结论和易错点留在画面上。

板书文字应该做到：

- 比老师讲解更短。
- 比普通标题更有教学信息。
- 能独立支撑学生回忆这一页讲过什么。
- 和视觉焦点、讲解锚点处在同一版式关系里。
- 在页面推进时逐步出现，而不是一次性堆满。

禁止两个极端：

- **无板书**：画面只有图像和声音，学生漏听后没有可回看的结构。
- **讲稿上屏**：把老师要说的话整段贴出来，挤压视觉主体和节奏。

判断标准是：学生暂停在这一页时，能不能通过板书文字快速复述“这页讲了什么、结论是什么、下一步要做什么”。

### 4.4 展示与交互技术准入

教学内容的展示本身是核心能力，不应被简化成“图 + 字 + 老师念稿”。

项目可以引入外部成熟的展示、动画和交互手段，包括优秀开源库、教学仿真、可视化组件、游戏式演出、拖拽实验、动态图表、步骤回放和局部操控。但引入标准必须高，不能为了“有交互”而增加粗糙体验。

允许引入的技术必须同时满足：

- **优秀**：比项目自己临时实现更成熟、更稳定。
- **有设计感**：视觉层级、节奏、动效和操作反馈经过设计，不是默认控件堆叠。
- **有美感**：和课程舞台、学科气质、老师角色、板书文字协调。
- **准确**：不能用漂亮动画表达错误知识、错误比例、错误过程或错误因果。
- **顺畅**：操作响应、动画帧率、语音节拍和画面更新不卡顿。
- **可教学**：学生交互后必须得到解释、反馈或结论，而不是只看到效果。

外部技术进入项目后必须被封装成可复用的 `SceneTechnique`，不能散落成单页特殊代码。每个 `SceneTechnique` 都要说明适用知识类型、交互方式、准确性约束、性能边界和失败降级方案。

禁止引入：

- 只是好看但无法解释知识关系的动效。
- 拖拽、缩放、旋转后没有教学反馈的交互。
- 精确学科内容依赖不可靠生图或近似动画。
- 帧率不稳、点击延迟明显、语音和画面不同步的展示。
- 与主舞台视觉语言冲突的外部组件原样嵌入。

判断标准是：这个技术是否让学生更准确、更顺畅、更有兴趣地理解教学内容，而不是让页面显得“更高级”。

### 4.5 一条主线

项目主线固定为：

```
教材 / 知识点
  → 教学目标
  → 教学骨架
  → 课堂脚本
  → 教学画面
  → 课堂演出
  → 学习反馈
```

所有模块都必须能说清自己服务这条链路的哪一环。

### 4.6 少模式，高质量

保留两种核心体验模式即可：

| 模式 | 用途 | 状态 |
| --- | --- | --- |
| 备课模式 | 老师审目标、骨架、脚本、画面 | 核心 |
| 上课模式 | 16:9 舞台，老师带学生走完整课程 | 核心 |

学生一个人使用时，不再叫“自学模式”。它应该是上课模式里的“个人跟课”场景：

- 仍然由老师或系统教学角色讲解。
- 仍然有提问、等待、反馈和纠错。
- 学生可以控制节奏，但不是自己看材料。
- 答错后进入补教片段，而不是只显示答案。

暂不作为核心：

- 独立放映模式。
- live 多人实时课堂。
- media remix。
- 整课视频导出。
- 复杂 PPTX 编辑器。

这些能力可以保留代码，但入口进入“实验区”，不能影响主流程。

### 4.7 骨架优先，LLM 填槽

课程质量不能主要依赖 prompt 长度。

生成策略改为：

- 系统先识别知识类型和教学类型。
- 命中教学骨架后，用骨架确定页面序列。
- LLM 只填每页需要的教材内容、例子、讲稿和反馈。
- 未命中骨架时，可以临时生成候选骨架，但必须标为候选，不进入默认库。

### 4.8 课堂舞台统一

所有教学画面使用固定逻辑画布：

- `1920×1080`
- 16:9
- 所有课堂角色、对白、控制、提问都在画面内
- 内容密集时自动退回紧凑头像或纯字幕
- 角色立绘使用脱底类 PNG 图像，不放在头像框或卡片里强行包装
- 角色层必须能换位、缩放、退场或降级，不能一直压住教学内容

课堂不是网页滚动页，也不是 PPT 外面挂一堆 UI 控件。

### 4.9 角色、音色与年级适配

角色造型和音色不是皮肤配置，而是教学可信度的一部分。

同一位老师、学生或教学角色必须保持稳定的视觉身份和声音身份。不同年级、学科和课型可以变化，但变化必须合理，不能只是随机换形象、换声音或换语气。

必须匹配：

- **角色身份**：老师像老师，学生像对应年级学生，旁白像讲解者，不混淆教学功能。
- **学段年龄**：小学、初中、高中的角色成熟度、表情夸张度、语言密度和互动节奏不同。
- **学科气质**：语文可以更有文学感，数学和科学要更清晰、克制、准确。
- **音色稳定**：同一角色在同一课程内不能频繁变声。
- **语速和情绪**：低年级更慢、更鼓励；高年级更简洁、更有推理感。
- **表达难度**：年级变化要体现在词汇、句长、追问深度、板书密度和例题复杂度上。

禁止：

- 用同一套角色造型和音色覆盖所有年级。
- 老师声音在同一节课里随机变化。
- 小学课使用过度成人化、压迫感强的讲解方式。
- 初中或高中课仍使用幼儿化表情、语气和互动。
- 角色造型好看但身份、学段或学科不可信。

判断标准是：学生一眼能相信“这个人在教我这个年级应该学的内容”，一听能确认“这个声音就是这个角色”。

#### 同学角色的作用

同学不是用来让画面热闹的，也不是随机插话的第二讲解员。

同学的核心作用是代表真实学生的学习状态，让老师有对象可教，让学生能看到“别人也会这样想、这样错、这样被纠正”。

同学角色可以承担：

- **提问者**：把学生可能不敢问的问题说出来。
- **误区暴露者**：说出典型错误理解，让老师当场纠偏。
- **尝试作答者**：先给出不完整答案，引出改进过程。
- **同伴复述者**：用学生语言复述老师刚讲的内容，检验是否听懂。
- **情绪缓冲者**：在难点处表达困惑、紧张或恍然大悟，降低学习压力。
- **比较对象**：展示两种思路、两种答案或两种观察方式的差异。

同学不能承担：

- 替代老师连续讲解。
- 无目的地插科打诨。
- 只表达“好厉害”“我懂了”这类空反馈。
- 在内容密集页长期占据画面。

判断标准是：删掉同学这句话后，如果教学没有任何损失，这句话就不应该出现。

#### 老师自选与科目适配

老师可以让学生或用户自选，但“老师身份”不等于“所有科目都用同一种表现”。

同一位老师应保持稳定人格、造型识别和主音色，同时允许按科目出现合理变化：

- 语文：语言更有节奏和审美感，适合朗读、意象、情感和文本细读。
- 数学：表达更克制、结构更强，强调定义、条件、推理链和步骤。
- 科学：更像实验引导者，强调观察、变量、证据和结论。
- 英语：语音准确性、节奏、语境和模仿反馈更重要。
- 历史 / 地理：更强调时间、空间、因果和证据材料。

变化可以体现在：

- 服装细节、道具、站姿和板书方式。
- 语速、停顿、强调方式和课堂气质。
- 提问方式、举例方式和纠错方式。
- 展示技术偏好，例如语文偏文本细读，数学偏步骤推导，科学偏仿真和观察。

不能出现：

- 用户选了一个老师后，所有科目都像同一节泛泛讲座。
- 为了科目变化把老师变成另一个人，导致造型和音色身份断裂。
- 科目变化只换背景或道具，不改变讲解方式。

## 5. 新产品架构

### 5.1 信息架构

建议只保留 4 个一级入口：

1. **课程库**
   - 已生成课程。
   - 课程状态。
   - 质量状态。
   - 最近真实检查结果。

2. **新建课程**
   - 选择教材 / 粘贴主题。
   - 选择学段、科目、课型。
   - 明确本节课只解决什么问题。

3. **备课工作台**
   - 目标。
   - 骨架。
   - 脚本。
   - 画面。
   - 质量检查。

4. **上课**
   - 老师课堂授课。
   - 学生个人跟课。
   - 学习反馈。

以下入口降级：

- PPTX 导出：放在课程详情里的次级操作。
- present 放映态：合并进上课模式。
- live：实验区。
- media remix：实验区。
- skeleton approve：备课工作台里的高级操作。

### 5.2 创作流程重设计

现有 7 步过长，建议收敛为 4 步：

#### Step 1：定课

用户只确认三件事：

- 教什么。
- 教到什么程度。
- 不教什么。

输出：

- 课程范围。
- 目标用户。
- 1-3 个可验证学习目标。
- 知识边界。

#### Step 2：定骨架

系统给出一个教学骨架，而不是先生成自由节目单。

用户看到：

- 这节课属于什么知识类型。
- 采用什么教学弧线。
- 每页承担什么教学动作。
- 哪些页是图示、例题、提问、总结。

用户可做：

- 换骨架。
- 删除浪费页。
- 改顺序。
- 明确必须出现的教材证据。

#### Step 3：定脚本和画面

系统按骨架生成：

- 每页画面主体。
- 老师讲解。
- 学生误区或追问。
- 提问与反馈。
- 图示 / 配图策略。

用户重点检查：

- 有没有复读。
- 有没有悬空引用。
- 图像是否真的对应内容。
- 学生错误是否真实。

#### Step 4：真实检查后上课

系统先跑质量闸门，再允许进入正式上课。

检查结果分三类：

- 阻断：必须修。
- 警告：建议修。
- 观察：记录但不挡。

只有通过后进入正式上课。

学生个人使用也进入上课模式，只是切换为“个人跟课”节奏：系统保留讲解、提问、反馈和补教，不提供无人教学的材料浏览模式。

## 6. 核心数据模型重排

建议把概念层级固定下来：

```
Course
  LessonGoal[]
  TeachingSkeleton
  LearningFragment[]
    Scene[]
      Beat[]
```

### 6.1 Course

课程只保存稳定结果：

- topic
- audience
- gradeBand
- subject
- source material
- goals
- boundary
- selected teacher
- teacherSubjectProfile
- peerRoleProfile
- castProfiles
- voiceProfiles
- gradeAdaptationProfile
- quality status

其中：

- `gradeBand` 固定本课学段和年级范围，例如小学低段、小学高段、初中或高中。
- `teacherSubjectProfile` 保存用户所选老师在当前科目里的讲法、气质、板书方式、展示技术偏好和音色细节。
- `peerRoleProfile` 保存同学角色在本课中的功能边界，例如提问者、误区暴露者、尝试作答者、同伴复述者或情绪缓冲者。
- `castProfiles` 保存老师、学生、旁白、同桌等角色的稳定造型、身份和表情体系。
- `voiceProfiles` 保存每个角色稳定的音色、语速、情绪范围和 TTS 配置。
- `gradeAdaptationProfile` 保存本课面向该年级的语言难度、互动密度、板书密度、讲解节奏和角色成熟度。

### 6.2 TeachingSkeleton

骨架是课程主结构。

必须包含：

- knowledgeType
- teachingType
- arc
- required visual forms
- required checks
- non-goals

### 6.3 LearningFragment

片段是学生真正学习的最小单元。

规则：

- 45-120 秒。
- 1-5 个 scene。
- 有目标、有成功信号。
- 可单独复习。

### 6.4 Scene

替代当前混乱的 atom 语义。

Scene 是“一个教学画面”，必须有：

- sceneType
- visualLayout
- contentSlots
- visualFocus
- narrationAnchor
- syncStrategy
- boardText
- sceneTechnique
- interactionContract
- fallbackPresentation
- characterLayer
- dialogueLayout
- peerFunction
- subjectTeachingMode
- voiceCue
- gradeTone
- teacherScript
- studentAction
- evidenceOnScreen

其中：

- `visualFocus` 说明这一页学生首先要看的对象。
- `narrationAnchor` 说明老师讲解绑定到画面中的哪个对象、词句、步骤或区域。
- `syncStrategy` 说明讲解和画面如何同步，例如逐行显现、局部放大、路径追踪、左右对照、色彩高亮、指针停留或角色退场。
- `boardText` 说明需要留在画面上的板书文字，例如提纲、关键词、步骤、结论和易错点。
- `sceneTechnique` 说明这一页使用的展示或交互技术，例如静态板书、分步推导、可拖拽示意、动态图表、局部放大、对照滑块、时间轴或仿真实验。
- `interactionContract` 说明学生能操作什么、系统如何反馈、老师如何解释操作结果。
- `fallbackPresentation` 说明外部技术不可用或性能不达标时，如何退回到准确的静态讲解版。
- `characterLayer` 说明角色是否出现、使用哪个角色、哪个表情、立绘位置、大小和退场条件。
- `dialogueLayout` 说明对白采用半身立绘、紧凑头像、底部 RPG 对话、旁白字幕还是无角色讲解。
- `peerFunction` 说明同学在当前 scene 中承担提问、误区、尝试作答、复述、情绪缓冲还是比较对象。
- `subjectTeachingMode` 说明老师在当前科目中采用文本细读、步骤推导、实验观察、语音模仿、材料证据或空间推理等讲法。
- `voiceCue` 说明当前 scene 的角色声音使用、情绪强度、语速和停顿。
- `gradeTone` 说明当前 scene 的语言密度、追问深度和互动节奏是否符合目标年级。

没有视觉焦点、讲解锚点、同步策略、必要板书、展示技术说明、角色对话层策略、同学功能、科目讲法、音色提示和年级语气，scene 不能进入正式上课。

### 6.5 Beat

Beat 是 scene 内部的演出节拍。

只负责：

- reveal
- speak
- point
- ask
- wait
- react

Beat 不应该再承担课程结构职责。

## 7. 生成管线重设计

### 7.1 旧问题

当前生成侧存在多层补丁：

- rundown prompt 很长，承担过多规则。
- skeleton 既是提示注入，又有硬骨架路径。
- atoms-only 还会自由生成具体页面。
- fragment-quality 再修补。
- backfill-images、backfill-beats 再补资产和节拍。

这会导致：

- 质量依赖多个补丁是否都命中。
- 每次修一个问题都会增加一条规则。
- 用户很难知道问题发生在哪一层。

### 7.2 新管线

```
1. analyze-source
   输入教材/主题，输出知识边界和候选目标。

2. choose-skeleton
   确定 knowledgeType + teachingType + skeleton。

3. compile-lesson
   根据 skeleton 生成 fragments / scenes 的结构，不自由扩写。

4. fill-scenes
   LLM 填每个 scene 的内容槽、讲稿、反馈、视觉焦点、讲解锚点、板书文字、同学功能、科目讲法、音色提示和年级语气。

5. technique-plan
   为 scene 选择展示或交互技术，明确是否需要静态板书、分步推导、动态图表、拖拽示意、局部放大、对照滑块、时间轴或仿真实验。

6. compile-beats
   把 scene 编译成课堂节拍，并保证每个 speak / point / reveal 都有对应画面对象。

7. asset-plan
   决定哪些图必须结构化绘制，哪些可以生图，哪些不需要图。

8. quality-gate
   失败则回到对应层修，不做黑箱 repair。
```

### 7.3 质量修复原则

不再默认“repair 一切”。

修复分层：

- 结构错：回骨架层。
- 内容错：回填槽层。
- 讲稿错：回脚本层。
- 同学角色错：回 peer role profile。
- 科目讲法错：回 teacher subject profile。
- 年级语气或音色错：回角色 / voice profile。
- 展示技术错：回 technique plan。
- 图像错：回 asset plan。
- 渲染错：回组件层。

禁止把所有问题都交给一个“修复接口”重写。

## 8. 体验重设计

### 8.1 备课工作台

备课工作台应像“教案审阅”，不是流程向导堆表单。

推荐布局：

- 左侧：课程结构树。
- 中间：当前页画面预览。
- 右侧：检查与修改面板。

每页显示：

- 画面主体。
- 老师讲解。
- 学生动作。
- 对应目标。
- 质量问题。

用户主要动作：

- 删除浪费页。
- 合并重复页。
- 改讲解。
- 换版式。
- 重新生成本页。

### 8.2 上课模式

上课模式只有一个核心界面：

- 16:9 课堂舞台。
- 顶部最小控制。
- 右下角页码 / 节拍进度。
- 角色和对白在舞台内。
- 内容密集页自动用紧凑对白。

上课模式不应该再同时存在“普通 AtomRenderer 页”和“BeatStage 页”的视觉断裂。

### 8.3 个人跟课与练习反馈

个人跟课不是自学，也不是上课模式换个壳。

它应该突出“被教”的体验：

- 片段选择。
- 学习进度。
- 老师讲解。
- 等待学生回答。
- 做题反馈。
- 错题补弱点。
- 必要时插入补教片段。

个人跟课的情绪是“被带着走”和“被关注”，不是“自己翻材料”，也不是“课堂热闹”。

界面上可以比课堂授课更轻，但教学角色不能消失：

- 老师半身立绘可以退为头像。
- 对白可以退为紧凑字幕。
- 提问和反馈必须保留。
- 学生答错后必须回到对应知识缺口。

### 8.4 放映 / PPTX

放映和 PPTX 是输出能力，不是主产品体验。

规则：

- 不能反向影响课堂舞台设计。
- 不能为了 PPTX 牺牲教学节拍。
- 只输出已经通过质量闸门的课程。

## 9. 视觉系统重设计

### 9.1 舞台规则

所有课堂画面按固定舞台设计：

- 逻辑尺寸：1920×1080。
- 内容安全区：左右 96px，上 72px，下 96px。
- 角色安全区：左右边缘和底部。
- 关键内容优先级高于角色。
- 对白有三档：RPG 半身、compact 头像、caption 字幕。

### 9.2 版式系统

保留少量稳定版式：

| 版式 | 用途 |
| --- | --- |
| 原文 / 题干主视觉 | 古诗、题目、定义 |
| 图 + 证据栏 | 意象、观察、实验 |
| 结构图 + 解释栏 | 几何、科学结构 |
| 分步板书 | 推导、计算、证明 |
| 对比判别 | 易混概念 |
| 问答反馈 | 判断、纠错 |
| 总结卡 | 复习与收束 |
| 角色对话 | 引导、追问、误区、情绪承接 |
| 中央内容 + 侧边角色 | 内容主体强、需要老师陪伴讲解 |
| 角色退场 + 纯内容 | 古诗原文、题干、公式、复杂图示 |
| 旁白 + 局部标注 | 需要最大化展示空间的讲解 |

每个版式有可变参数，但不允许随意堆卡片。

每个正式教学页应有一层“板书文字”设计，但不等于每页都要大段文字。板书可以是：

- 课题或本页问题。
- 关键词和定义。
- 步骤编号。
- 公式、诗句、题干或原文。
- 对比项和判断标准。
- 本页结论或易错提醒。

板书文字必须固定在版式里，不能像临时标注一样漂浮在画面上。它的层级应该低于视觉主体，高于装饰和角色对白。

版式选择必须由讲解路径决定：

- 老师要逐句讲，画面就逐句显现。
- 老师要比较，画面就做并列或对照。
- 老师要指出细节，画面就做局部放大或指针停留。
- 老师要推理，画面就做路径、步骤或因果链。
- 老师要让学生作答，画面就先留出回答空间，再显示反馈。
- 老师要收束，画面就留下可复述的板书结论。

不能先选一个好看的模板，再把讲稿硬塞进去。

这条不仅适用于语文古诗，也适用于绝大多数内容类型：数学推导、科学实验、历史时间线、英语语法、写作修改、图像观察、例题讲解都需要先设计内容呈现关系，再决定角色是否出现、出现多大、站在哪边。

### 9.3 色彩与高亮

只保留语义色。

- 已知 / 概念：蓝
- 操作 / 推理：橙
- 结论 / 正确：绿
- 错误 / 风险：红
- 审美 / 语言：紫

颜色不能用于随机装饰。

### 9.4 角色对话层

游戏化对话界面不是固定的底部对话框，而是一套可切换的角色对话层。

角色资产规则：

- 老师、学生和关键教学角色必须有明显不同的外形、姿态、服装气质和表情体系。
- 角色应使用脱底类 PNG 立绘，优先是半身或大半身，不用方形头像框包住。
- 每个常用角色至少需要基础、思考、强调、鼓励、疑问、纠错等多种表情。
- 角色边缘、光影和色调要能融入课程舞台，不能像贴纸一样漂浮。
- 角色不是装饰物，出场必须对应讲解、提问、反馈、情绪承接或误区纠正。
- 角色造型必须匹配年级、学科和教学身份，不能所有课程复用同一套成熟度。
- 同一角色的音色必须稳定，表情变化可以明显，声音身份不能漂移。
- 年级变化要体现在造型成熟度、语速、停顿、鼓励方式、追问深度和语言密度上。
- 同学角色必须声明本页教学功能，不允许作为气氛角色随机出现。
- 老师可以由用户自选，但必须加载当前科目的 `teacherSubjectProfile`。

角色对话层至少支持这些版式：

| 角色版式 | 用途 |
| --- | --- |
| 左侧老师立绘 + 右侧内容 / 板书 | 老师主讲、内容需要跟随讲解 |
| 右侧学生立绘 + 左侧内容 / 反馈 | 学生提问、暴露误区、等待反馈 |
| 双角色分侧 + 中央内容 | 对话推动理解，但中央内容仍是主体 |
| 底部 RPG 对话 + 上方内容 | 情绪承接、短句互动、过渡页 |
| 角落头像 + 紧凑字幕 | 内容密集页、例题页、原文页 |
| 旁白字幕 + 无角色 | 需要完整展示题干、古诗、图表或公式 |
| 角色临时入场 / 退场 | 只在关键讲解、提问、反馈时出现 |

角色版式必须让出教学内容：

- 不遮挡 `visualFocus`。
- 不遮挡 `boardText`。
- 不遮挡交互控件、图表坐标、题干、原文、公式和关键标注。
- 内容需要完整呈现时，角色必须退为头像、旁白或完全退场。
- 同一节课内允许多套角色版式切换，但切换必须服务讲解节奏。

判断标准是：角色让课程更像有人在教，而不是让学生看不见正在被教的内容。

### 9.5 展示与交互技术库

展示技术应该形成可复用库，而不是每节课临时拼装。

可优先沉淀的技术类型：

| 技术类型 | 适用场景 |
| --- | --- |
| 分层显现 | 定义、古诗赏析、结构拆解 |
| 局部放大 | 字词、图像细节、几何关系 |
| 路径追踪 | 推理、证明、过程、因果链 |
| 对照滑块 | 改写前后、错误与正确、图像变化 |
| 时间轴 | 历史、情节、实验过程 |
| 可拖拽示意 | 几何、物理、空间关系 |
| 动态图表 | 函数、统计、变化趋势 |
| 仿真实验 | 科学实验、变量观察 |
| 步骤回放 | 解题、书写、操作流程 |

这些技术可以来自外部优秀库或成熟案例，但进入 maolab 后必须重新适配：

- 使用 1920×1080 舞台安全区。
- 使用项目统一字体、色彩、高亮和板书层。
- 支持老师讲解、指向、暂停、回放和提问。
- 有明确的无交互降级版。
- 通过真实检查后才能进入默认可选库。

不接受外部组件原样嵌入后破坏整体视觉，也不接受只在演示时惊艳、真实上课时卡顿或难操作的交互。

## 10. 技术架构重整

### 10.1 模块分层

建议分为 5 层：

1. `domain`
   - 课程、目标、骨架、片段、场景、节拍的纯类型与规则。

2. `generation`
   - analyze、skeleton、compile、fill、asset plan。

3. `quality`
   - 静态检查、真实检查记录、阻断规则。

4. `runtime`
   - 上课、个人跟课、播放状态、TTS、互动、音色档案。

5. `presentation`
   - 16:9 舞台、版式组件、展示技术库、角色造型库、角色对白、导出适配。

外部展示与交互技术只能进入 `presentation` 层的技术库，由 scene 通过 `sceneTechnique` 引用。禁止业务流程、生成器或单页组件直接依赖零散外部实现。

### 10.2 需要拆的文件

当前文件超过健康边界，应拆：

- `PresentMode.tsx`：1518 行，应拆成播放器框架 + stage registry + 各 scene stage。
- `BeatStage.tsx`：855 行，应拆成状态机、对白层、提问层、节拍执行器。
- `SlotPresenters.tsx`：637 行，应拆成 scene layout registry。
- `rundown.ts`：639 行，应拆成 skeleton compile、LLM fallback、post processors。
- `fragment-quality.ts`：600+ 行，应拆成独立规则包。

### 10.3 需要收拢的路径

合并或明确边界：

- `AtomRenderer` 与 `PresentMode`：避免同一 atom 两套渲染逻辑漂移。
- `LectureMode` 与 `BeatStage`：统一课堂舞台，不再普通页一套、beat 页一套。
- `showscript` 与 `script-only`：明确一个脚本来源。
- `show-planner` 与 `rundown`：明确哪个是主结构。
- `live`：移入实验区。

## 11. 质量闸门重设计

质量闸门分六类：

### 11.1 教学闸门

- 是否定义先行。
- 是否单概念推进。
- 是否每页自足。
- 是否目标有验证。
- 是否误区有纠偏。

### 11.2 画面闸门

- 讲解对象是否在画面上。
- 视觉焦点是否清楚。
- 讲解锚点是否明确。
- 画面变化是否跟随讲解节奏。
- 是否有必要的板书文字。
- 板书文字是否比讲稿更短、更结构化。
- 图文是否冲突。
- 文字是否溢出。
- 版式是否跳动。
- 是否用了正确专用渲染器。

以下问题应判为阻断：

- 老师讲解的对象不在画面上。
- 讲解顺序和视觉显现顺序相反。
- 当前视觉焦点被角色、对白、浮层或标注遮挡。
- 画面同时出现多个重点，但讲解没有建立主次。
- 文字只是贴在图上，没有通过版式说明关系。
- 应该有板书的页完全没有可回看的关键词、步骤或结论。
- 板书变成整段讲稿，导致学生不知道该看图、看字还是听老师。

### 11.3 表演闸门

- TTS 是否干净。
- 老师是否复读。
- 学生发言是否有承接。
- 对白是否压住主体。
- 角色立绘是否遮挡教学内容。
- 角色表情是否匹配当前讲解、提问或反馈。
- 内容密集时角色是否能退为头像、旁白或退场。
- 停顿和反馈是否存在。

以下问题应判为阻断：

- 角色或对白连续遮挡 `visualFocus`、`boardText`、题干、原文、公式、图表或交互控件。
- 所有角色使用同一视觉气质，无法区分身份和教学功能。
- 半身立绘在不需要情绪承接的内容页持续占据主要画面。
- 对白层只有固定一种版式，导致不同内容类型都被同一套 UI 压住。

### 11.4 资产闸门

- 功能图是否结构化。
- 配图是否真实存在。
- 生图是否不承载精确信息。
- IP 是否与科目和老师绑定一致。

### 11.5 角色、音色与年级适配闸门

- 角色造型是否符合学段、年级、学科和教学身份。
- 老师、学生、旁白、同桌等角色是否有可区分的视觉功能。
- 同学角色是否有明确教学功能，而不是随机插话。
- 同学发言是否暴露真实疑问、误区、尝试、复述或情绪状态。
- 用户自选老师是否加载了当前科目的讲法与表现变体。
- 同一老师跨科目变化是否合理，且不破坏角色身份和音色稳定。
- 同一角色音色是否稳定，是否避免同课随机变声。
- TTS 语速、停顿、情绪强度是否符合年级。
- 低年级是否有足够鼓励、等待和重复确认。
- 高年级是否避免幼儿化表达，讲解是否更简洁、有推理层次。
- 年级变化是否体现在语言密度、板书密度、提问深度和互动节奏上。
- 角色表情是否匹配讲解状态，不把严肃知识讲成娱乐表演。

以下问题应判为阻断：

- 同一老师在一节课中音色明显漂移。
- 同学只负责附和、卖萌或制造热闹，没有推动教学。
- 同学连续替代老师讲解，导致教学主次混乱。
- 用户自选老师后，语文、数学、科学等科目仍使用同一种泛化讲法。
- 科目变化只换背景或道具，不改变讲解方式、展示偏好和纠错方式。
- 小学课使用过度成人化、压迫感强或语速过快的声音。
- 初中或高中课使用幼儿化角色、语气和互动。
- 角色造型无法让人判断其教学身份或目标年级。
- 年级切换只改标签，不改讲解方式、板书密度和互动难度。

### 11.6 展示与交互技术闸门

- 技术是否真正服务本页教学目标。
- 交互是否有明确反馈、解释和结论。
- 动效是否和老师讲解节拍同步。
- 操作是否顺畅，点击、拖拽、回放没有明显延迟。
- 视觉是否有设计感和美感，且不破坏主舞台语言。
- 知识表达是否准确，比例、顺序、因果、公式、图形关系不能误导。
- 外部技术是否被封装为可复用 `SceneTechnique`。
- 是否有静态或低性能降级方案。

以下问题应判为阻断：

- 交互只是炫技，学生操作后没有教学反馈。
- 动效漂亮但表达了错误知识过程。
- 组件视觉风格和课程舞台明显割裂。
- 操作卡顿、拖拽不跟手、动画掉帧或打断 TTS 节奏。
- 外部组件原样嵌入，无法被质量闸门检查。

闸门输出必须指向修复层：

- 改骨架
- 改页面
- 改讲稿
- 改图像
- 改渲染
- 改展示技术

## 12. 阶段计划

### Phase 0：止血

目标：停止继续扩散。

- 标记核心入口与实验入口。
- 禁止新增平行课堂模式。
- 旧整课视频继续隔离。
- 新功能必须绑定主线。

交付：

- 项目重启设计文档。
- 核心 / 实验 / 隔离功能清单。

### Phase 1：统一课堂舞台

目标：所有上课画面共用一套 16:9 舞台和版式系统。

- 合并普通 atom 与 beat atom 的视觉差异。
- 建立 scene layout registry。
- 建立角色对话层版式族，不只做固定 RPG 对话框。
- 建立角色造型与音色档案库。
- 建立 SceneTechnique 展示与交互技术库。
- 对白三档正式成为系统能力。
- 上课模式成为唯一正式播放体验。

成功标准：

- 同一课程不会出现两套视觉语言。
- 翻页、提问、对白、讲稿控制位置稳定。
- 半身立绘、头像、旁白、无角色状态能按内容密度自然切换。
- 同一角色在同一课程内造型和音色稳定。
- 展示和交互技术有统一准入、统一封装和降级方案。
- 真实检查不再出现遮挡主体和布局跳动。

### Phase 2：骨架主导生成

目标：LLM 不再自由编排课程。

- TeachingSkeleton 成为必经层。
- rundown 改为 compile lesson。
- 展示技术选择进入 technique-plan，不再后补特效。
- 年级适配进入 gradeAdaptationProfile，不再只靠 prompt 语气描述。
- 未命中骨架进入候选，不直接污染主库。
- 移除靠 prompt 堆叠的重复规则。

成功标准：

- 同一知识类型生成结构稳定。
- 简单课不会被加复杂剧情壳。
- 重复页和包装页显著减少。

### Phase 3：备课工作台

目标：老师能看懂并改动课程质量。

- 结构树。
- 画面预览。
- 脚本编辑。
- 质量问题定位。
- 单页重生成。

成功标准：

- 用户能在 5 分钟内判断一节课是否可上。
- 用户能删除、合并、修改问题页。
- 系统能解释为什么某页被判为问题。

### Phase 4：个人跟课与反馈闭环

目标：让学生一个人使用时仍然被教，而不是自己看材料。

- 学生按片段跟课。
- 老师讲解、提问、等待和反馈保留。
- 答题结果进入 objective / KP 反馈。
- 错误触发补弱点片段。
- 课堂角色可以降级为头像或字幕，但不能完全消失。

成功标准：

- 学生答错后不是只显示答案，而是回到对应知识缺口。
- 学习记录能影响后续播放顺序。

### Phase 5：输出能力恢复

目标：在主流程稳定后恢复导出。

- PPTX 只作为上课内容的导出适配。
- 视频只按片段 + beat 渲染。
- media remix 只从通过质量闸门的片段生成。

成功标准：

- 导出不再引入低质量旧流程。
- 视频画面和讲解同步。

## 13. 功能去留表

| 功能 | 新状态 | 原因 |
| --- | --- | --- |
| 教材 / KP | 核心 | 产品地基 |
| 教学目标 | 核心 | 课程边界 |
| TeachingSkeleton | 核心 | 稳定质量 |
| Rundown | 改名 / 收拢 | 应变成 lesson compile 结果 |
| Script-only | 核心但收拢 | 变成 scene script |
| Atoms-only | 改名 / 收拢 | 变成 scene fill |
| BeatStage | 核心但拆分 | 课堂演出层 |
| LectureMode | 核心但统一 | 正式上课入口 |
| SelfStudyMode | 取消 / 合并 | 不再作为独立模式，改为上课模式里的个人跟课场景 |
| PresentMode | 降级 / 合并 | 不应成为平行体验 |
| PPTX 导出 | 次级 | 输出能力 |

| media remix | 实验区 | 容易抢主线 |
| 旧视频导出 | 隔离 | 已证明污染质量 |
| repair-grounding | 隔离 | 曾造成复读机 |

## 14. 成功标准

### 产品标准

- 用户能明确知道：这节课教什么、怎么教、哪里可改。
- 生成课程默认可上，不需要大量人工救火。
- 角色、图像、媒体不再喧宾夺主。
- 角色有差异化立绘和表情，但能按内容需要退让。
- 同学角色能暴露疑问、误区、尝试和复述，推动老师教学。
- 角色造型、音色、语言难度和年级认知水平一致。
- 用户自选老师后，不同科目仍有合理讲法变化。
- 老师像在教学，不像朗读页面。
- 优秀外部展示与交互技术可以进入课程，但必须准确、美观、顺畅、可教学。

### 工程标准

- 核心课堂渲染只有一套舞台系统。
- 角色对话层有统一布局规则和降级机制。
- 同学角色和老师科目变体通过 profile 约束，不靠临时 prompt 发挥。
- 角色造型和音色通过档案绑定，不在课程播放中随机变化。
- 展示与交互技术通过 SceneTechnique 统一封装。
- 单个关键文件不再超过 800 行。
- 质量问题能定位到生成层或渲染层。
- 新功能必须有归属层和质量闸门。

### 真实检查标准

每次只评三件事：

1. 学生是否听懂。
2. 老师是否真在教。
3. 画面是否支撑讲解。

第三项必须包含板书检查：学生暂停页面时，是否能通过画面中的关键词、步骤或结论复述本页内容。

如果使用展示或交互技术，还必须检查它是否准确、顺畅、有设计感，并且真的帮助学生理解。

如果使用角色对话层，还必须检查角色是否有差异化、是否使用脱底立绘、是否在内容密集时退让，以及是否帮助教学而不是遮挡教学。

还必须检查角色造型、音色、语速、表达难度和目标年级是否一致。

同学角色还要检查是否真的暴露了学习状态；老师角色还要检查自选身份和当前科目讲法是否同时成立。

如果三项不达标，禁止用“更漂亮的 UI / 更多角色 / 更多媒体”掩盖。

## 15. 暂不做

- 不做完整实时多智能体课堂。
- 不做整课视频导出。
- 不做复杂 PPT 编辑器。
- 不做角色养成系统。
- 不做每科都单独一套视觉宇宙。
- 不做无法被质量闸门验证的装饰型媒体。

## 16. 下一步执行建议

第一轮不要直接大改生成器。

建议顺序：

1. 写 `CORE_VS_EXPERIMENTAL.md`，把入口分成核心、实验、隔离。
2. 在代码里建立 `Scene` / `LessonScene` 的类型草案，不迁移数据。
3. 抽出统一 `StageCanvas`、`DialogueLayer` 和 `SceneTechnique` 注册表。
4. 先做角色对话层样板：左师右文、右生左文、双角色中央内容、角落头像、旁白无角色。
5. 建立同学角色功能样板：提问、误区、尝试作答、同伴复述、情绪缓冲。
6. 建立老师科目变体样板：同一老师至少覆盖语文、数学、科学三种讲法。
7. 建立角色造型 / 音色 / 年级适配样板：小学低段、小学高段、初中至少各一套。
8. 先做 5 个展示技术样板：分层显现、局部放大、路径追踪、对照滑块、步骤回放。
9. 选 2 门课做样板：一门小学，一门初中；一门文科，一门理科。
10. 用新舞台和新质量闸门真实检查。
11. 再迁移生成管线。

这一轮的目标不是“一次性重写项目”，而是让项目重新有边界、有主线、有可验证的质量标准。

## 17. 仍需补强的设计缺口

前面的规则已经把课程主线、视觉呈现、角色、音色、年级适配和质量闸门收住了。下一步还需要补强的是“长期不会再跑偏”的能力。

### 17.1 学习效果证据

现在文档强调“学生是否听懂”，但还需要定义听懂的证据。

每个 LearningFragment 应该至少有一个可观察信号：

- 学生能复述关键词、步骤或结论。
- 学生能完成一个小判断、小填空或小操作。
- 学生能指出一个错误在哪里。
- 学生能把本页结论迁移到相邻例子。

禁止只用“讲完了”“播放完了”“学生点了下一页”代表学会。

### 17.2 错因与补教闭环

答错后不能只进入泛化解释。

系统需要记录：

- 错在概念不清。
- 错在步骤遗漏。
- 错在看错题干或图像。
- 错在语言理解。
- 错在计算或操作。

补教片段应该对应错因，而不是统一播放“再讲一遍”。

### 17.3 教材证据与来源治理

课程必须能说明关键内容来自哪里。

需要区分：

- 教材原文。
- 题干 / 例题。
- 系统生成解释。
- 老师补充例子。
- AI 生成图片。
- 外部资源或开源展示技术。

凡是教材原文、古诗、题干、定义、公式、历史材料、实验数据，都应保留来源或证据字段。生图和装饰素材不能承载精确信息。

### 17.4 无障碍与多感官降级

课程不能只服务视觉或听觉状态良好的学生。

至少要保证：

- 所有 TTS 有可读字幕。
- 关键讲解有板书摘要。
- 颜色高亮不能是唯一信息通道。
- 动画和交互有暂停、回放和低动效版本。
- 角色退场后仍能看懂教学主线。
- 内容密集页不依赖细小文字。

无障碍不是额外功能，而是教学可靠性的一部分。

### 17.5 黄金样板课与回归检查

项目需要少量长期稳定的黄金样板课，用来防止后续改动破坏质量。

建议至少保留：

- 小学语文古诗。
- 初中语文古诗或文言。
- 小学数学概念。
- 初中数学推导。
- 小学科学观察。
- 初中科学实验或变量。

每次改生成管线、舞台、角色、TTS、版式或展示技术，都必须用这些样板课跑真实检查。

### 17.6 版本、差异与回滚

备课工作台不能只支持“重新生成”。

需要支持：

- 本页修改前后对比。
- 讲稿差异。
- 板书差异。
- 画面布局差异。
- 质量问题变化。
- 一键回到上一个可上版本。

否则用户会害怕修改，因为每次重生成都可能把已经调好的部分破坏掉。

### 17.7 课堂运行可靠性

正式上课时，技术失败比设计不漂亮更致命。

需要定义：

- TTS 失败时如何继续上课。
- 角色立绘加载失败时如何降级。
- 交互组件卡顿时如何退回静态讲解。
- 图片生成失败时如何使用结构化占位或板书替代。
- 网络慢时是否能先播放已缓存片段。

每个 SceneTechnique、角色层和音频层都应有降级方案。

### 17.8 需求优先级治理

以后新增能力必须先回答四个问题：

1. 它服务哪一个学习目标？
2. 它改善的是讲解、画面、反馈、练习还是备课？
3. 它是否能进入现有 Scene / Beat / Quality Gate 模型？
4. 它失败时会不会破坏正式上课？

答不清的功能只能进入实验区，不能进入主流程。

## 18. 重启执行方式

可以重新开始，但不是推倒旧代码。

正确方式是“壳内重启”：保留当前仓库、依赖、已有资产、可运行服务和已验证能力，但新产品主线不再服从旧代码结构。

### 18.1 旧代码的新定位

旧代码不再是产品结构的来源，只作为资产库和迁移来源。

旧能力分三类：

| 类型 | 处理方式 |
| --- | --- |
| 可直接复用 | 教材 / KP、已有教师资产、TTS 接入、部分质量规则、已有展示组件 |
| 需要适配 | rundown、atoms、beats、旧课堂渲染、旧课程数据 |
| 暂停 / 隔离 | live、media remix、旧整课视频、平行 present 体验、黑箱 repair |

原则：

- 新功能不再直接接入旧 atom / rundown 结构。
- 旧代码只能通过 adapter 进入新 Course / Scene / Beat 模型。
- 旧入口可以保留运行，但不再承载新产品判断。
- 所有迁移都以“是否服务新主线”为准，不以“旧代码已经有”为准。

### 18.2 新主线从哪里开始

新主线只从四个核心对象开始：

```text
Course
  TeachingSkeleton
  LearningFragment
    Scene
      Beat
```

先建立这四个对象的最小可运行链路，再逐步迁移旧能力。

第一条样板链路应该是：

```text
输入主题 / 教材
  → 选择教学骨架
  → 生成 3-5 个 Scene
  → 通过 StageCanvas 呈现
  → 老师讲解 + 板书 + 角色层
  → 质量闸门
  → 真实检查
```

不要一开始就恢复所有模式、所有导出、所有旧课程。

### 18.3 新旧并行边界

允许短期并行，但边界必须清楚：

| 区域 | 规则 |
| --- | --- |
| 旧 v2 课程 | 只保留查看、回放、必要修 bug |
| 新课程 | 只走新 Course / Scene / Stage / Quality Gate |
| 旧生成器 | 只作为迁移参考，不继续堆 prompt |
| 新生成器 | 骨架优先，scene 填槽，质量闸门阻断 |
| 旧 UI | 不再作为新体验标准 |
| 新 UI | 统一 1920×1080 教学舞台 |

如果新旧都能做同一件事，以新主线为准。

### 18.4 第一阶段不做什么

重启早期必须克制。

第一阶段不做：

- 不迁移全部旧课程。
- 不恢复所有旧入口。
- 不做完整导出。
- 不做 live。
- 不做 media remix。
- 不做多套视觉宇宙。
- 不做大规模批量生成。

先把一节课做对，再扩展到十节课。

### 18.5 第一条垂直切片

第一条垂直切片建议只做一门课。

要求：

- 一个明确知识点。
- 一个目标年级。
- 一个老师。
- 一个同学功能角色。
- 3-5 个 Scene。
- 至少 2 种版式。
- 至少 1 个 SceneTechnique。
- 全程 1920×1080。
- 有板书、有讲解、有提问、有反馈。
- 通过质量闸门和真实检查。

这条切片做通后，再做第二门课：不同年级、不同科目，用来验证模型是否真的可复用。

### 18.6 代码落地顺序

建议代码从这些文件或模块开始：

1. `CORE_VS_EXPERIMENTAL.md`
   - 明确核心、实验、隔离入口。

2. `domain`
   - 定义 `Course`、`TeachingSkeleton`、`LearningFragment`、`Scene`、`Beat`。

3. `presentation`
   - 建立 `StageCanvas`、`DialogueLayer`、`SceneTechnique` registry。

4. `quality`
   - 建立教学、画面、表演、资产、角色音色、展示交互六类闸门。

5. `adapters`
   - 只负责把旧数据转成新模型，不让旧结构污染新主线。

6. `samples`
   - 建立黄金样板课和回归检查。

### 18.7 重启成功标准

重启不是“新建目录”或“换一套路由”。

真正成功的标准是：

- 新课不依赖旧 atom / rundown 的自由生成逻辑。
- 一节课能从 Course 走到 Stage，再走到 Quality Gate。
- 老师讲解、画面、板书、角色和互动能同步。
- 质量问题能定位到骨架、scene、讲稿、资产、角色或渲染层。
- 旧代码可以继续存在，但不再决定产品方向。

到这一步，项目就算重新开始了。
